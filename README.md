## Problem and rationale
Our cooking assistant aims to help users decide what to eat. It will consider preferences, available ingredients, serving counts, and time when proposing meals. LLMs help interpret natural-language requests and feedback, ask clarifying questions, and explain recommendations. The audience is people who cook for themselves or others and need help deciding what to eat; success criteria still need team review.

## Planned LLM integration
An agent will use explicit tools to retrieve recipes, read inventory, validate meal plans, and revise proposals based on results. Quantity calculations and inventory writes will be handled by deterministic application logic. The planned product model is Google Gemini Developer API `gemini-3.5-flash-lite`, free tier only (account access remains to be verified during Construction); OpenAI Codex is the planned development assistant, using AI-DLC v1.0.1.

## Proposed scope and feasibility
The proposed product supports personalized five-day menus covering breakfast, lunch, and dinner, a recipe library, manually maintained inventory, shopping-list generation, and changes to meals. Users can select a dish they actually cooked, review and correct estimated ingredient usage, and confirm inventory deductions. The agent can then suggest adjustments to remaining meals. Menus are suggestions that users can dynamically adjust at any time; planning does not consume inventory. Users customize party size, and the agent proposes an appropriate combination of dishes and scaled quantities, subject to user changes. Cookware constraints are excluded.

The local technical baseline is Python 3.12, FastAPI, Streamlit, SQLite, and pytest. Recipes are retrieved from a source-attributed local collection (RAG), supplemented by supported public recipe URLs. General live search is conditional on a separately verified free service.
